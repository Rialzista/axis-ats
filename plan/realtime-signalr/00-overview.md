# Realtime (SignalR) — Фаза 3

## Цель

Показать реальное умение работать с WebSocket-based realtime: когда один рекрутер двигает кандидата
по Kanban, все остальные открытые сессии (другие вкладки/браузеры), смотрящие ту же вакансию, видят
перемещение карточки мгновенно — без ручного refresh и без polling.

Не отдельная неделя — 2 дня поверх уже готового `PATCH /api/pipeline-entries/{id}` (Фаза 2, День 11).
Если не хватит времени физически смотреть на реальный browser-to-browser эффект — тестировать двумя
вкладками одного браузера, этого достаточно для демонстрации.

## Почему SignalR, а не голый WebSocket

SignalR поверх WebSocket (с fallback на Server-Sent Events/long polling, если WS недоступен) даёт из
коробки: группы соединений (нужны, чтобы рассылать событие только тем, кто смотрит конкретную вакансию,
а не всем подряд), автопереподключение на клиенте, строготипизированный контракт методов через
`HubConnection.On<T>`/`IHubContext<T>.Clients`. На .NET это идиоматичный выбор для такой задачи —
голый `System.Net.WebSockets` оправдан, если нужен полный контроль над бинарным протоколом или
совместимость с не-.NET клиентом без SignalR-библиотеки, что здесь не требуется.

## Проблема "нет авторизации" и демо-трюк

В проекте нет аутентификации (осознанно вне скоупа Фазы 2), поэтому нечем убедительно показать "два
разных рекрутера видят изменения друг друга" — если оба таба анонимны, эффект не читается зрителем.

**Решение**: добавить лёгкую фейковую идентичность на фронте — в `Topbar` выпадающий список
"Acting as: <User>" (список тех же 5 `User` из сид-данных), выбор кладётся в `localStorage`, все
мутации (`MoveStageAsync`, `AddNote`) передают `actorId` из этого выбора вместо хардкода. Это не
авторизация (никакой защиты, просто выбор персоны для демо), но именно то, что делает realtime-эффект
наглядным: открываете два окна браузера, в одном выбираете Recruiter A, в другом Recruiter B, двигаете
карточку в одном — видите мгновенное обновление и подпись "moved by Recruiter B" в другом.

## Контракт события

Один hub, один тип события на первой итерации — не усложнять сразу многими каналами:

```
Hub route: /hubs/pipeline

Client → Server (invoke):
  JoinJobGroup(jobId: string): Task
  LeaveJobGroup(jobId: string): Task

Server → Client (on):
  CandidateStageChanged(payload: {
    pipelineEntryId: string;
    jobId: string;
    candidateId: string;
    candidateFullName: string;
    fromStageId: string;
    toStageId: string;
    movedAt: string;          // ISO date
    actorId: string;
    actorFullName: string;
  }): void
```

Группа — `job-{jobId}`, ровно как area видимости в UI (страница `/jobs/:id` и `/pipeline` с выбранной
вакансией). Сервер рассылает событие только этой группе, не broadcast всем подключениям.

## Definition of Done

- [ ] Два открытых окна браузера на одной вакансии: перетаскивание карточки в одном мгновенно двигает
  её во втором, без перезагрузки
- [ ] В карточке видно, кто последний передвинул кандидата ("moved by <actor>")
- [ ] Отключение сети/сервера и восстановление — клиент автоматически переподключается и досинхронизирует
  состояние (не остаётся в рассинхроне молча)
- [ ] Собственное действие пользователя не дублируется/не мигает при получении эха своего же события
  обратно через хаб
