# Event contract — детали

## Порядок событий при перемещении карточки

1. Пользователь A перетаскивает карточку в UI → фронт применяет **optimistic update** локально
   (уже реализовано в Фазе 1, День 5) → отправляет `PATCH /api/pipeline-entries/{id}`
2. Бэкенд обновляет `PipelineEntry` и создаёт `ActivityEvent` (уже реализовано в Фазе 2, День 11) →
   **дополнительно** публикует `CandidateStageChanged` в группу `job-{jobId}` через `IHubContext`
3. HTTP-ответ на PATCH возвращает пользователю A подтверждение — его optimistic update либо
   подтверждается, либо откатывается при ошибке (как и раньше)
4. **Все члены группы, включая самого пользователя A**, получают `CandidateStageChanged` через хаб —
   это важный момент: сервер не различает "отправителя" и "остальных", событие летит всем в группе

## Проблема эха и дедупликации на клиенте

Пользователь A получит через хаб то же событие, которое он только что сам инициировал — если
применить его наивно поверх уже применённого optimistic update, ничего не сломается по данным, но
может дёрнуться UI (лишний ре-рендер/мигание). Обработка на клиенте (детали — в `16-day-16`):

- Хранить в памяти клиента последний **локально инициированный** `pipelineEntryId` + `toStageId` с
  коротким TTL (несколько секунд)
- При получении события через хаб — если `pipelineEntryId`+`toStageId` совпадает с недавним локальным
  действием, применить его "тихо" (обновить `movedAt`/`actorFullName`, если отличаются, без визуального
  скачка карточки, которая и так уже в нужной колонке)
- Во всех остальных случаях — обновлять состояние как обычно

## Reconnect и рассинхронизация

SignalR клиент переподключается автоматически (`withAutomaticReconnect()`), но **события, пропущенные
во время разрыва соединения, не доставляются задним числом** — это не персистентная очередь сообщений,
а pub/sub поверх живого соединения. Поэтому:

- При событии `onreconnected` клиента — не полагаться на то, что состояние актуально, а сделать
  `queryClient.invalidateQueries(['job-pipeline-entries', jobId])` (полный рефетч через уже
  существующий REST-эндпоинт) — WebSocket-канал ускоряет happy path, но не заменяет REST как источник
  истины при восстановлении
- Аналогично при первом подключении к группе (`JoinJobGroup`) — сначала обычный REST GET для
  первоначальной загрузки данных (как уже сделано), хаб только уведомляет об изменениях **после** того,
  как страница уже открыта

## Что не входит в контракт (сознательно, чтобы не раздувать скоуп)

- Presence ("кто сейчас смотрит эту вакансию") — не делаем, отдельная фича, не подтверждённая в
  обсуждении вариантов
- События для Notes/Activity через хаб — можно добавить позже по тому же паттерну, но не в рамках
  этих 2 дней, чтобы не размазывать фокус
- Персистентная доставка пропущенных событий (message queue/outbox) — избыточно для проекта,
  инвалидации через REST при reconnect достаточно
