## Пошаговые задачи

1. **Тестовый проект**
   - `dotnet new xunit -n Ats.Api.Tests -o tests/Ats.Api.Tests`, добавить ссылку на `Ats.Api`
   - Установить `Microsoft.AspNetCore.Mvc.Testing`
   - `CustomWebApplicationFactory.cs` — наследник `WebApplicationFactory<Program>`, переопределяет
     `ConfigureWebHost` чтобы подменить строку подключения на **отдельную тестовую БД** (не бить по
     той же БД, что используется для ручной разработки — иначе тесты будут удалять/пересоздавать ваши
     сид-данные). Вариант попроще: тестовый Postgres в том же `docker-compose.yml` на другом порту,
     или Testcontainers (`Testcontainers.PostgreSql`) — если хочется потренировать более "правильный"
     подход к изоляции тестов, но для проекта фиксированная тестовая БД тоже приемлема

2. **Тестовые сценарии — минимум**
   - `CandidatesEndpointsTests`:
     - `GET /api/candidates` возвращает 200 и непустой список
     - `GET /api/candidates?search=<часть имени существующего кандидата>` возвращает отфильтрованный
       результат
     - `GET /api/candidates/{несуществующий guid}` возвращает 404
     - `POST /api/candidates/{id}/notes` с валидным телом возвращает 201/200 и созданную заметку;
       с пустым `text` — 400
   - `MoveStageTests`:
     - `PATCH /api/pipeline-entries/{id}` с валидным `stageId` меняет стадию и создаёт `ActivityEvent`
       (проверить через последующий `GET /api/candidates/{candidateId}/activity`)
     - `PATCH` с несуществующим `stageId` возвращает 400
     - `PATCH` с несуществующим `id` записи пайплайна возвращает 404

3. **Dockerfile для бэкенда**
   - Multi-stage build: стадия `build` (`mcr.microsoft.com/dotnet/sdk:8.0`) — `dotnet publish`, стадия
     `runtime` (`mcr.microsoft.com/dotnet/aspnet:8.0`) — копирует опубликованные файлы, `ENTRYPOINT
     ["dotnet", "Ats.Api.dll"]`
   - Проверить локально: `docker build -t ats-api .` + `docker run -p 5000:8080 ats-api` (сверить порт,
     на котором слушает контейнер по умолчанию в .NET 8 — обычно 8080 внутри контейнера)

4. **Деплой бэкенда**
   - Выбрать хостинг с поддержкой Docker-контейнеров и бесплатным тиром: Fly.io, Railway или Render
   - Настроить переменные окружения на хостинге: строку подключения к БД (хостинг обычно даёт managed
     Postgres тем же провайдером — не поднимать свою БД руками на проде, использовать managed)
   - Применить миграции на прод-БД (`dotnet ef database update` с прод connection string, либо через
     `migrationsEndpoint`/init-контейнер — на ваш выбор, для проекта ручной прогон миграции один раз
     — нормально)
   - Убедиться, что сидер **не запускается** на проде при каждом рестарте (либо сделать сид только для
     Development, либо явно защитить идемпотентностью, которая уже была реализована на Дне 9 — второе
     надёжнее)

5. **Финальное подключение фронтенда**
   - Обновить `baseURL` в проде фронтенда (переменная окружения Vite, `VITE_API_URL`) на прод-URL бэкенда
   - Обновить CORS-политику на бэкенде: добавить прод-домен фронтенда к разрешённым origin (Дню 8
     настраивали только localhost)
   - Убедиться, что `schema.d.ts` (сгенерированный в День 13 из OpenAPI) актуален относительно
     финальной версии бэкенда — перегенерировать при необходимости
   - Передеплоить фронтенд с новой переменной окружения

6. **Сквозная ручная проверка (End-to-end чеклист)**
   - Открыть прод-фронтенд → Dashboard показывает данные
   - Открыть Candidates → найти кандидата через поиск → открыть профиль → добавить заметку → заметка
     видна в ленте
   - Открыть Jobs → открыть вакансию → перетащить кандидата в Kanban на другую стадию → обновить
     страницу → изменение сохранилось
   - Открыть Reports → построить отчёт → экспортировать CSV

7. **README — финальная версия**
   - Обновить корневой `README.md` (или добавить `backend/README.md`): архитектура (диаграмма папок),
     как поднять всё целиком локально (`docker-compose up` + `dotnet run` + `npm run dev`), ссылки на
     задеплоенные фронт и бэк, явное указание, что дизайн вдохновлён Axis HRM (Behance)
